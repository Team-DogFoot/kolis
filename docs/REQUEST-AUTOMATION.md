# 요청 방식 자동화 — 가능한 범위 (2026-09-29 분석)

용어
- **화면 방식**: 프로그램이 Edge 의 KOLIS 화면에서 버튼을 누르고 글자를 넣는 방식. 지금까지 만든 KOLIS 단계가 전부 이 방식이다.
- **요청 방식**: 화면을 누르지 않고, 화면이 버튼을 눌렀을 때 KOLIS 서버로 보내는 것과 같은 내용을 프로그램이 직접 보내는 방식.
- **요청 기록**: 화면이 서버와 주고받은 내용(주소, 보낸 값, 받은 값)을 남긴 파일. `work/captures/rec/<시각>/requests.jsonl`. 저장소와 PC 밖으로 내보내지 않는다.

근거: 타임머신 대소동(접수번호 939 → 가원부번호 2026-1615)을 화면 방식으로 끝까지 진행하면서 받은 요청 기록 223줄(요청 36건, 확인창·알림창 11건, 팝업 4건, 폼 전송 4건).

## 1. 요청을 어떻게 보내는가

| 방법 | 가능 여부 | 이유 |
|---|---|---|
| 프로그램이 따로 접속(HTTP 클라이언트) | **지금은 불가** | 로그인 상태를 나타내는 쿠키를 화면의 스크립트에서 읽을 수 없다(화면에서 보이는 쿠키 7개 중에 세션 쿠키가 없음). 따로 로그인하려면 로그인 요청의 형식을 알아야 하는데 기록이 없다(로그인된 상태에서 시작했음). 계정을 프로그램이 다루게 되는 점도 있다 |
| **로그인된 KOLIS 화면 안에서 보냄** | **가능(채택)** | 직원이 로그인해 둔 Edge 의 KOLIS 화면에 스크립트를 넣어 그 화면이 요청을 보내게 한다. 로그인 상태를 그대로 쓰므로 계정·쿠키를 다루지 않는다. 마우스·키보드·창 위치와 무관하다 |

채택한 방법의 조건: Edge 에 KOLIS 화면이 로그인된 채로 하나 열려 있어야 한다(어느 메뉴든 상관없음). 알림창이나 팝업이 떠 있으면 그 뒤의 화면은 멈춰 있어 쓸 수 없다.

## 2. 단계별 판정

| 업무 단계 | 화면이 보내는 요청 | 요청 방식 | 상태 |
|---|---|---|---|
| 메뉴 이동 | `POST /cmmn/menu/openCheck.do` (menuCode, menuSe) → 이동할 주소 | 필요 없음 | 요청 방식은 화면을 옮기지 않는다 |
| **일괄반입**(반입용 엑셀 올리기) | `POST /online/reg/bo/accrectarget/fileUpload.do` (파일 첨부 형식. 항목: acquisit_code, acquisit_year, work_code, working_status, har_stat_cd, desc(비고), file_name(파일), work_dir_path …) → `{"receiptno": 접수번호}` | **불가** | 화면의 스크립트는 PC 의 파일을 스스로 집어 보낼 수 없다(브라우저의 보안 제한). 따로 접속하는 방법이 열리면 가능 |
| 반입 결과 확인(접수번호, 건수) | `…/onlineDepstRecet/getReceiptKeyByRcptNo.do`, `…/selectMultipleOnlineDepstrecetList.do` | 가능 | 아래 '전체출력'과 같은 요청 |
| **전체출력**(콘텐츠ID 받기) | 서버에 묻지 않는다. 화면이 목록을 XML 로 만들어 `/main/save.do` 로 보내고 파일로 되받는다 | **가능** | 목록 요청의 응답에 건별 콘텐츠ID·원문 수·MODS 전문이 들어 있다. `kolis_request.export_receipt` — 만든 표가 실제 전체출력 파일과 같음을 확인 |
| 폴더명을 콘텐츠ID 로 | (KOLIS 와 무관, PC 안의 일) | — | 기존 그대로 |
| **원문일괄등록** — 폴더 전송 | 업로더(DEXT5)가 파일을 서버의 임시 위치로 보낸다. 이 전송은 요청 기록에 잡히지 않았다 | **불가** | 파일 전송 + 형식 미확인 |
| 원문일괄등록 — 전송 뒤 | `/online/cmmn/setFileList.do`(업로더가 돌려준 파일 목록) → 폴더마다 `getfileList.do`, `getTocFile.do`, `searchTextCheck.do`, `updateTextCheck.do`, `insertContentsText.do` | 옮기지 않음 | 형식은 다 기록됐지만 앞 단계(전송)가 팝업 안에서 일어나므로 팝업에서 이어서 하는 것이 맞다. 걸리는 시간도 짧다(3건 6초) |
| 원문 등록 확인 | 목록 요청의 CNT_FILES(원문 수) | **가능** | `kolis_request.contents` |
| 썸네일 등록 | 기록 없음(이번 납품은 썸네일이 없었음) | 미정 | 파일 전송이라 불가일 가능성이 높다 |
| **등록대상처리** | `POST …/onlineDepstRecet/updateTargetProcessing.do` (JSON: receipt_key, species_key[], contents_id[], isbn[], work_code, checkYn) | **가능** | `kolis_request.target_process` — 만든 본문이 기록과 글자 단위로 같음 |
| **가원부번호 발급** | `POST /online/reg/bo/accrecmake/onlineAccRecMake/selectAccRecMakeListWithParam.do`(목록) → `POST …/popup/insertTempAccessionRecNo.do` (작성년도, 등록구분 FTX, species_keys, receipt_keys, 원문서비스구분 07) → `{"temp_accession_rec_no": 번호}` | **가능** | `kolis_request.make_record` — 본문이 기록과 같음 |
| **가원부 파일**(등록원부관리 전체출력) | `POST /online/reg/bo/accrecmng/onlineAccRecMng/selectAccRecMngListWithParam.do` | **가능** | `kolis_request.export_record` — 만든 표가 화면에서 받은 가원부 파일과 같음(열 17개, 3행 전부) |
| MODS XML 받기(점검용) | 목록 응답의 CONTENTS_XML | **가능(접수 상태일 때)** | `export_receipt` 가 `work/xml/<콘텐츠ID>.xml` 로 저장. 등록대상처리 뒤에는 납본자료접수 목록에서 빠지므로 구축·점검 단계에서는 다른 화면(디지털콘텐츠관리)의 요청을 기록해야 한다 |
| 복본 판정, 구축(전거·주제명), 점검 | 기록 없음 | 미정 | 그 단계를 화면 방식으로 처음 진행할 때 기록이 남는다 |

요약: **파일을 보내는 두 단계(일괄반입, 원문일괄등록)는 화면 방식으로 남고, 나머지(목록 읽기, 등록대상처리, 가원부번호, 가원부 파일)는 요청 방식으로 옮길 수 있다.**

## 3. 만든 것 (`kolis_tool/kolis_request.py`)

- 프로그램 3단계 "요청 방식으로 받기" 버튼: 접수번호의 목록을 받아 `work/접수번호 N.xlsx` 와 `work/xml/` 을 만든다. KOLIS 의 자료를 바꾸지 않는다.
- 프로그램 5단계 "방식" 선택: 화면 방식(기본) / 요청 방식. 요청 방식은 등록대상처리 → 가원부번호 → 가원부 파일을 요청만으로 한다.
- 바꾸는 요청(등록대상처리, 가원부번호)의 안전 장치: YES 입력 필수. 보내기 전에 목록을 읽어 조건을 확인한다(전 건이 '접수' 상태인가, 전 건에 원문이 있는가, 등록구분이 FTX 인가, 이용대상·서비스범위가 섞이지 않았는가, 건수가 KOLIS 가 알려 준 수와 같은가). 보낸 뒤 다시 읽어 확인한다. 하나라도 다르면 보내지 않고 멈춘다.
- 요청 방식 작업은 Edge 창을 조작하지 않으므로 프로그램 창을 내리지 않고 "한 번에 한 작품" 잠금도 걸지 않는다(여러 작품 동시 가능). 단, 화면 방식 작업이 도는 동안에는 받지 않는다(그 작업이 화면을 옮기면 요청이 끊긴다).

## 4. 확인한 것과 확인하지 못한 것

확인함(저장된 기록과 받은 파일로. KOLIS 에 보내지 않음. `kolis_request.check_saved()`):
- 이 코드가 만드는 요청 본문 5종이 기록된 본문과 같다.
- 기록된 응답으로 만든 접수 목록 표가 실제 전체출력 파일과 같다(가격의 통화 기호와 받은 시점이 다른 원문갯수 제외). 폴더명 단계가 읽는 값(접수번호 ↔ 콘텐츠ID)이 같다.
- 기록된 응답으로 만든 가원부 표가 화면에서 받은 가원부 파일과 전부 같다.

**확인하지 못함**(실제로 보내야 알 수 있음):
- 화면 안에 스크립트를 넣어 요청을 보내고 응답을 받아 오는 부분(`Page.send`). 같은 방법으로 기록용 스크립트를 넣는 것은 09-29 에 계속 썼지만, 요청을 보내는 것은 한 번도 실행하지 않았다.
- 등록대상처리를 요청으로 보냈을 때 화면의 확인 절차 없이 그대로 처리되는가(화면에서는 대화 상자와 확인창 2개를 거친다. 기록상 서버로 가는 것은 요청 1건뿐).
- 업무구분 62(납본 단행), 수입구분 1 이 아닌 자료. 코드는 이 값으로 고정돼 있다.

첫 실제 실행은 직원 입회 아래 실제 작품으로 한다. 순서: ① 3단계 "요청 방식으로 받기"(읽기만 함)로 `Page.send` 를 먼저 확인 → ② 5단계를 요청 방식으로. 재료는 추풍낙엽(5권).
