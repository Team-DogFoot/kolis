## 1. 에이전트(반입용 엑셀) — 무엇을 어떻게 고치나

### 1-2. 가이드 조항 중 스킬에 없는 것 → 스킬에 조항 번호와 원문으로 넣는다
- 1.1 외국어 표제 대소문자, 관제 원괄호 / 1.2 시즌·외전은 표제관련정보 / 1.3 프롤로그·에필로그는 권차 비우고 권차표제 / 1.6 대등표제.
- 2 저자: 채택 순서 **원문 › 기초메타데이터 › 플랫폼(각괄호)**, 유형 개인명/단체명, 단체명 수식어 생략, 2.1 전거형이 있으면 저자명은 전거형, 2.2 전거형과 원문 표기가 다르면 디스플레이형식, 2.3 역할어 명사형, 2.4 다른이름 유형(nickname / formal name / no specific type).
- 5 출처정보: 발행처 › 제작처 순, 5.1 발행지 단위명 제외·추정은 각괄호, 5.2 영문 발행처 첫 글자만 대문자, 발행지가 다른 제작처는 둘째 출처정보에 `[제작]`, 5.4 판사항.
- 9 주기 순서와 유형별 문구. 13 ISBN 은 seoji 에서 파일형식·발행처 확인, UCI 는 엑셀에 넣지 않음. 14.1 원문주소 둘 다, 연재처 소멸이면 비움.
- 2.1 의 "전거형"을 알려면 전거 조회가 필요하다. 전거 **번호**는 엑셀에 넣지 않되, 이름을 전거형으로 적기 위해 프로그램이 저자마다 전거 후보를 요청(`listACMat.do`, 읽기)으로 받아 에이전트에 넘긴다. 에이전트는 KOLIS 에 접근하지 않는다. 판단 결과(전거 번호·확신·근거)는 작업 폴더 `decisions.json` 에 두어 3-2 가 쓴다.

### 1-3. 검사(`check-import`)에 넣을 것
발행처·저자 각괄호 금지(산출에서 `[KOCN]` 나온 적 있음) / 원문주소 1번이 도메인 루트(`https://ridibooks.com`)면 거부 — 가이드 14.1 은 연재처 메인+작품 상세 / 권차가 단위 없는 숫자만이면 원고 표기 대조 요구 / 역할어 관형형 거부 / 발행처가 둘인데 임프린트 주기가 없으면 확인 요구 / 영문 발행처 전체 대문자 경고.

### 1-4. 시험(채점 아님)
- 예시 파일의 값을 `import.json` 꼴로 역변환해 양식 쓰기로 다시 쓴 뒤 **예시와 셀 단위로 같은지** 확인 — 양식 쓰기가 88열을 그대로 낼 수 있는지 보는 시험.
- 스킬 수정 뒤 유저가 준 시험 폴더(원시인 삼촌 등) 하나로 1 단계를 돌려 산출을 가이드 조항별로 대조해 보고(불일치 항목과 조항 번호).

## 2. 3-2 — 확인과 한 번에 입력

### 2-1. 확인(가이드 5.3 첫 문장: "콘텐츠를 한 건씩 열어 반입용 기초메타데이터 파일대로 MODS 항목에 잘 들어갔는지 확인")
- 원부의 콘텐츠마다 MODS XML 을 요청으로 읽어(`getHarContentsXml.do`, 읽기만) 반입용 엑셀의 값과 칸마다 대조한 표를 3-2 에 둔다. 열: 회차 · 칸 · 반입값 · KOLIS 값 · 같음/다름. 전부 같으면 "n건 모두 같음" 한 줄.
- 반입값은 작업 폴더의 반입용 엑셀에서 읽는다(작업 폴더가 없는 작품은 KOLIS 가 돌려주는 반입 원값).

### 2-2. 한 번에 입력 — **무엇을 입력하나**(가이드 5.3 둘째 문장과 그림 25~28)
반입용 엑셀로는 못 넣어 KOLIS MODS 화면에서만 되는 항목. 콘텐츠마다 같은 값이 들어가므로 원부 단위로 한 번에 넣는다.

| 항목 | MODS 자리 | 값 | 어디서 정하나 |
|---|---|---|---|
| 저자전거 연결 | 저자정보 `@ID`, `@전거(authority)` | 전거 번호(예 KAC201418251), `국립중앙도서관전거데이터`, 유형 personal | 1-2 의 `decisions.json`(강한 확신인 저자만). 없는 작품은 3-2 작품 판단 |
| 저자 다른이름 | 저자정보 › 다른이름(`alternativeName`, `@altType`) | 원문에 본명·필명 등이 있을 때만, 유형 nickname/formal name/no specific type | 같음 |
| 주제명 연결 | 주제명 `@ID`·`@전거` + 장르주제명 | 일반주제명 만화 `KSH1998022212`, 장르주제명 웹툰[webtoon] `KSH2016000049`, 전거 `국립중앙도서관주제명표목표` | 사업 고정값 |
| 식별기호 UCI | 식별기호(유형 uci) | seoji 에서 찾은 UCI(있을 때만) | `decisions.json`(회차마다) |
| 이용제한(성인물) | 종 화면 이용제한구분 | 청소년 유해매체물 | 이미 자동(성인물 판단 뒤) |
| 그림 25·27 의 표제·권차·권차표제·출처정보 | 반입으로 들어가는 칸 | 2-1 의 대조에서 **다를 때만** 고침 | 대조 표 |

### 2-3. 어떻게 한 번에 넣나
1. **공용사항관리**(매뉴얼 16쪽: "여러 콘텐츠의 MODS 데이터를 일괄입력") — 디지털콘텐츠관리 메뉴. 아직 열어 본 적 없어 **화면·요청을 먼저 조사**(열기만, 저장 안 함). 전거 @ID·주제명·UCI 를 받으면 원부 단위 요청 한 번.
2. 안 되면 콘텐츠마다 **저장 요청**(`updateHarContents.do`, 형식 확정됨)을 프로그램이 만들어 보낸다: 현재 MODS 를 읽어 2-2 의 칸만 바꾼 평행 배열. 단추 하나로 N건.
3. 안전장치: 첫 1건을 보내고 전·후 XML 을 대조해 **의도한 칸만 바뀌었는지 확인한 뒤** 나머지를 보낸다. 끝나면 2-1 의 대조 표로 전체 검증. 요청·응답은 전부 기록.
4. 화면: 3-2 에 「n건에 한 번에 넣기」 단추 하나. 대화상자에 2-2 표의 내용을 이 작품 값으로 열거(예: "김성모 → KAC201418251 · 주제명 2묶음 · UCI 없음 · 8건").

## 3. 저장에 관한 약속(유저 지시 10-03)
- 조회(읽기) 요청은 필요하면 보낸다. **저장은 로직이 다 완성될 때까지 하지 않는다.**
- 완성되면 원부 **1614 의 2화부터** 저장한다(1화는 10-03 19:10 에 저장함). 이 작품은 **야맹장 전거 연결만 더 하면 바로 저장해도 되는 작품**이다(김성모 KAC201418251 은 프로그램 판단, 야맹장 KAC202574425 는 1화에서 직원이 연결한 값).
- 그래서 2-2 의 "어디서 정하나"에 **직원 결정**이 들어간다: 프로그램이 "연결 안 함(확신 보통)"으로 둔 저자를 직원이 화면에서 "연결(전거 번호)"로 바꿀 수 있어야 하고, 그 결정이 `decisions.json` 에 남아 한 번에 입력에 쓰인다. 1화 저장 XML 에서 야맹장의 전거 번호를 읽어 기본값으로 보여 준다.

## 6. 설계 리뷰 반영(2026-10-03, 서브에이전트 리뷰 8건 중 8건 수용 — 코드로 확인함)
1. **양식 현황 정정**: 83열 템플릿에 판사항(`edition`)과 둘째 출처정보 4열은 **이미 있다**. 예시 88열과의 실제 차이는 저자 4번째 묶음(+5열), 첫 출처정보의 둘째 발행처(+1), 그리고 템플릿의 `subject/topic` 2번째 열(예시에는 없음, −1). 1-1 의 "칸 없음" 두 줄은 틀렸음. 할 일은 "저자 묶음 반복 + 발행처 반복 + topic 2번째 열 제거"로 좁힌다.
2. **topic 2번째 열 `웹툰` 제거**: `import_writer.CONSTANTS[("/mods/subject/topic",1)]="웹툰"` 은 가이드 10 과 어긋난다(반입에는 일반주제명 `만화` 만, 웹툰은 구축에서 장르주제명). 3-2 `apply_subjects` 가 주제명 3묶음에서 멈추는 원인도 된다.
3. **저자 각괄호**: 플랫폼에서만 확인한 저자는 각괄호가 맞다(가이드 2). 검사는 `from` 이 플랫폼일 때만 허용, 그 외 거부. 발행처 각괄호 금지는 이미 있음.
4. **전거 후보 조회 방식**: 저자명은 에이전트가 원고·조사를 끝낸 뒤에 나오므로 미리 받을 수 없다. 프로그램이 제공하는 명령 `{PY} -m kolis_tool authority "<이름>"`(프로그램이 자기 로그인 세션으로 `listACMat.do` 조회, 읽기만, 결과를 파일로)을 에이전트가 부른다. 에이전트가 KOLIS 화면·계정에 직접 닿지는 않는다. 전거형 ≠ 원문이면 가이드 2.2 디스플레이형식(`displayForm`)이 필요한데 양식에 열이 없다 → **3-2 한 번에 입력 항목에 디스플레이형식 추가**(2-2 표), 둘째 출처정보의 발행지도 추가.
5. **결정 파일 하나로**: `decisions.json` 을 따로 두지 않고 3-2 의 작품 단위 `build.json`(이미 `check_build_work` 가 검사)로 통일. 항목마다 `source: agent | staff`. 1 단계 작업 폴더 ↔ 원부번호 짝은 탭 상태(`tabs.json`)에 적는다. 1 단계가 정한 전거형·성인물·UCI 는 그 build.json 의 초기값이 된다.
6. **직원 결정 전거가 버려지는 문제**: `apply_authors` 는 후보 목록에 없는 번호를 건너뛰고, `check_build` 는 high 확신·후보 포함을 요구한다 → 1614 2화에서 야맹장이 빠진다. `source: staff` 인 결정은 1화 저장 XML 의 `@ID`·채택표목을 그대로 담고 후보·확신 검사를 면제한다.
7. **저장 본문 생성 전제**: `updateHarContents.do` 는 화면 칸 id 목록(`inputedTableId` 290개)을 요구하므로 XML 만으로는 못 만든다. 콘텐츠의 수정 화면 폼(`form.json`, `read_form`)에서 만들어야 한다. ⑤에서 1화의 저장 전 폼으로 본문을 만들어 **기록된 1화 요청 본문과 같은지** 비교해 확정한다(쉼표 처리 포함). 전·후 XML 대조와 2-1 대조에는 KOLIS 가 스스로 바꾸는 값(internetMediaType, digitalOrigin, accessCondition, recordChangeDate…) 정규화 목록을 둔다.
