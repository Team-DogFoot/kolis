프로그램이 어떻게 동작하는지, 왜 느린지를 유저에게 설명하기 전에 **그 경로의 코드를 실제로 읽는다.** 클래스의 설명 글이나 기억으로 답하지 않는다. 그리고 질문에는 **먼저 예/아니오와 방법**을 답하고, 측정 방법이나 배경은 그 뒤에 둔다.

**Why:** 2026-10-01 에 "여러 작품이 접속 하나를 같이 써서 전송이 줄을 선다"고 두 번 설명했는데 틀렸다(실제로는 실행마다 접속을 따로 만들고, 여러 작품을 못 돌린 이유는 `app.py` 의 옛 화면 잠금이었다). 세 작품을 동시에 걸어 보고서야 알았다. 같은 날 유저가 "여러 작품을 동시에 하면 느려지나, 빠르게 할 방법이 있나"를 물었는데 측정 이야기를 길게 해서 "내 질문의 원래 의도를 모르겠어?"라는 말을 들었다.

**How to apply:** 원인·구조를 말하기 전에 호출 경로를 grep 해 읽고, 가능하면 실제로 돌려 본다. 답은 결론 한 줄 → 근거 → 선택지 순으로. 유저는 개발자라 기술 용어로 설명해도 되지만(TCP 연결, 세션 쿠키, 세마포어), 뭉뚱그린 말("접속")은 층을 나눠 말한다. 관련: [[say-unverified-and-blockers-first]] [[question-means-answer-only]] [[user-profile]]
