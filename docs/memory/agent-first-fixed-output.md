읽기·조사·판단은 **에이전트**가 한다. 고정 코드는 형태가 정해진 출력(MODS 83열 반입용 엑셀 쓰기)과 형식·파일 증거 검사에만 쓴다. 그리고 에이전트를 "긴 지시문을 넣고 답에서 JSON 을 뽑는 함수"로 쓰지 않는다.

**Why:** 2026-09-29 에 같은 실수를 세 번 되풀이해 유저가 크게 화냈다. ① 09-18 코드가 출판사 엑셀을 열 이름 고정으로 읽고 플랫폼을 3곳 고정으로 봐서 새 자료에서 바로 실패 ② 에이전트 결과가 실행마다 달라지자 원인(지시문에 판단 기준·완료 기준이 없음)을 고치지 않고 결론 규칙·필수 플랫폼 목록·정규식·보충 조사 단계를 파이썬에 넣음 → "왜 자꾸 결정론적으로 개선하려고 하느냐" ③ 에이전트 기능을 옵션 나열로만 이해 → "잘 쓰라는 게 스펙대로 쓰라는 게 아니다. 루프 엔지니어링, 스킬을 모르느냐". 유저는 웹백엔드·데브옵스 개발자이고 클로드코드를 잘 안다.

**How to apply:**
- 새 기능을 만들 때 "양식·사이트가 바뀌면 깨지는가"를 먼저 본다. 깨지면 코드로 만들지 않는다.
- 에이전트가 **스스로 돌게** 한다: 일 → 결과 파일 저장 → 검사 도구를 에이전트가 직접 실행 → 걸린 것을 읽고 고침 → 검수 에이전트(하위 에이전트) → 배운 것을 지식 파일에 기록. 프로그램이 이어서 시켜야 하면 새 실행이 아니라 `--resume` 으로 같은 대화를 잇는다.
- 판단 기준과 완료 기준은 **스킬 문서**에 적는다(도서관 매뉴얼 근거). 결과가 흔들리면 코드로 묶지 말고 기준·검수·지식을 고친다.
- 검사 도구는 판단하지 않는다(있는가, 근거 글자 안에 그 값이 있는가, 파일과 맞는가).
- 도서관 양식에 없는 중간 산출물(표준 엑셀, `_source` 시트)을 만들지 않는다. 단계도 업무에서 사람이 끼어드는 지점으로만 나눈다.
