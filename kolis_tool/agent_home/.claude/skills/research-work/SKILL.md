# 작품 조사

입력: `jobs/<작업>/job.json` 과 납품 자료에서 읽은 것(제목, ISBN, 납본 단위와 건수, 권차 표기, 출판사가 적은 값, 원고에서 직접 본 표기).
출력: `jobs/<작업>/research.json` (아래 "결과 파일").

## 0. 시작하기 전에
- `knowledge/platform-notes.md` 와 `knowledge/corrections.md` 를 읽는다. 같은 출판사·같은 플랫폼에서 이미 배운 것이 있다.
- 판단 기준이 헷갈리면 `knowledge/rules/` 의 매뉴얼 원문을 찾아 읽는다(Grep 으로 항목 이름 검색).

## 1. 도구
- WebSearch, WebFetch.
- 자바스크립트로 그려져 WebFetch 로 목록·날짜·가격이 안 보이는 페이지는 아래 명령으로 연다(이 PC 의 Edge 로 열어 화면 글자를 출력).
  `{PY} -m kolis_tool render "<주소>"`  옵션 `--scroll 10`(아래로 내려 목록을 더 불러옴), `--links`(링크 목록), `--find "등록일|출판사|이용가"`(그 단어가 든 줄과 앞뒤만. 정규식도 됨: `\d{4}\.\d{2}\.\d{2}`)
  명령 뒤에 `| grep` 같은 다른 명령을 잇지 않는다. 필요한 줄만 보려면 `--find` 를 쓴다.
- WebFetch 는 페이지를 요약해서 돌려주므로 날짜·가격 같은 **정확한 글자**는 render 로 직접 확인한다.

## 2. 무엇을 정하는가, 어떤 기준으로
매뉴얼(웹툰대행사업 매뉴얼 v1.6)의 기준이다.

| 값 | 기준 |
|---|---|
| 서비스 플랫폼 | 이 작품을 서비스하는(했던) 곳을 **찾을 수 있는 만큼 전부**. 매뉴얼이 예로 든 곳: 네이버시리즈, 리디, 카카오페이지, 레진코믹스, 봄툰, 포스타입, 북큐브, 유페이퍼, 부크크 / 판매처: 교보문고, 알라딘, YES24. 목록은 예시일 뿐이다. 출판사가 적은 플랫폼(예: 미스터블루)은 반드시 직접 연다. 작품이 없던 곳도 "찾아봤고 없었다"고 기록한다. |
| 같은 작품인가 | 제목이 같은 다른 작품이 흔하다. 저자·권(회차) 수·쪽수·출판사·표지로 같은 작품인지 확인한 뒤에만 값을 쓴다. 확인한 근거를 적는다. |
| 권·회차별 공개일 | 납본 단위 하나하나에 대해, 확인된 모든 플랫폼 중 **그 권·회차가 가장 이르게 공개된 날짜**. 플랫폼의 '등록일', '연재일', '공개일'이 해당한다. 작품 전체의 '업데이트', 전자책 '출간 정보'는 그 권의 공개일이 아닐 수 있으니 구분해서 본다. 한 화면에 날짜가 여러 종류면 전부 옮겨 적고 어느 것을 왜 골랐는지 쓴다. |
| 최초 연재 플랫폼 | 1번(첫 권·첫 회차)이 가장 이르게 공개된 플랫폼. 매뉴얼: "웹툰의 출처정보는 최초 발간된 웹툰과 그 플랫폼을 기준으로 한다." 출판사가 적은 값과 다르면 확인한 사실을 따르고 엇갈림으로 보고한다. 날짜가 같으면 출판사가 적은 곳. |
| 가격 | **권·회차마다 따로 찾는다**(한 회차의 값을 전체에 복사하지 않는다). 소장·대여·정액제가 다 있으면 **소장가가 정가**. 플랫폼마다 다르면 최초 연재 플랫폼의 가격. 코인·캐시는 원화로 환산하고 환산 근거를 적는다. '기다리면 무료'는 즉시 이용 가격. **무료로 공개된 회차(1화 무료 등)는 정가 0**(`free` 를 `무료`로). 서비스하던 플랫폼이 전부 문을 닫아 확인할 수 없으면 일괄 `550` 으로 하고, 어디를 찾아봤는지 적는다(직원 규칙 2026-10-01). |
| 이용등급 | 작품 정보에 **명시된** 등급 표기(전체 이용가, 12세, 15세, 19세·성인). 여러 플랫폼 중 **나이가 가장 많은 것**을 쓴다(A 15세, B 19세 → 19세). 플랫폼끼리, 또는 출판사가 적은 값과 다르면 엇갈림으로 보고. |
| 저자와 역할 | 글, 그림, 원작, 작화, 각색만. 어시스트·콘티·채색·배경·편집은 넣지 않는다(글·각색 표시가 없고 콘티만 있으면 콘티를 저자로). 한 사람이 글과 그림을 모두 맡았으면 역할은 `글·그림` 하나로 쓴다(완료 사례 표기). 원고 표기(으뜸정보원)가 플랫폼 표기보다 우선한다. |
| 발행처 | 최초 발간된 웹툰의 플랫폼 또는 출판사. 이름만 쓴다(화면의 '출판', '출판사' 같은 표시 문구는 이름이 아니다). 플랫폼 표기와 정식 법인명이 다르면 플랫폼 표기를 쓰고 정식 명칭은 메모에. 발행처에는 각괄호를 쓰지 않는다. |
| 발행처 소재지 | 시/도(예: 서울). 출판사 홈페이지, 사업자 정보, ISBN 서지정보(국립중앙도서관 서지정보유통지원시스템 `nl.go.kr/seoji`)에서 확인. |
| 장르 | 최초 연재 플랫폼 화면의 장르 표기 그대로. |
| 작품 소개 | 플랫폼 원문 그대로, 200자 이내. |
| 원문주소 | 지금 열리는 페이지여야 한다. 둘 다 적는다. **첫째: 그 작품이 들어 있는 목록 페이지**(만화·웹툰 등 분류 페이지. 예 `https://www.mrblue.com/comic`, `https://ridibooks.com/comics/ebook`. 플랫폼 첫 화면이 아니다). **둘째: 그 작품의 회차들이 보이는 페이지**(예 `https://www.mrblue.com/comic/C000075511`). 최초 연재 플랫폼이 사라졌으면 서비스 중인 다른 플랫폼. |
| ISBN | **권·회차마다 개별 ISBN** 을 찾는다(플랫폼 상세, 서지정보유통지원시스템 `nl.go.kr/seoji`, 판매처). 어디에서도 개별 ISBN 을 찾지 못하고 세트 ISBN 만 있으면 마지막 수단으로 세트 ISBN 을 쓰고 그렇게 적는다. 같은 권·회차에 ISBN 이 여럿이면(재출간 등) **출간일이 가장 이른 것**. 출판사 기초메타데이터가 틀린 경우가 있으므로 확인한 값이 다르면 확인한 값을 쓰고 엇갈림으로 보고한다. 붙임표(`-`) 없이 숫자만(직원 규칙 2026-10-01). |

## 3. 결과 파일 `research.json`
값마다 `evidence` 를 붙인다: 주소와 **화면에 적힌 글자 그대로**(`quote`). 날짜·가격은 quote 안에 그 숫자가 보여야 한다.

```json
{
 "title": "", "count": 0,
 "publisher_says": {"platform": "", "publisher": "", "audience": "", "isbn": "", "author": ""},
 "platforms": [{"name": "", "url_main": "", "url_work": "", "status": "서비스 중|서비스 종료|작품 없음|접속 실패",
                "same_work": "같은 작품이라고 본 근거", "start_date": "YYYYMMDD 또는 빈칸",
                "dates_on_page": [{"kind": "등록일|출간|업데이트|…", "date": "YYYYMMDD", "quote": ""}],
                "rating": "", "publisher": "", "genre": "", "isbn": ""}],
 "searched": [{"where": "찾아본 곳", "how": "검색어 또는 주소", "result": "무엇을 봤는지"}],
 "platform_first": "", "platform_first_reason": "기준에 따라 이렇게 정한 이유",
 "first_publish_date": "YYYYMMDD",
 "episodes": [{"no": 1, "date": "YYYYMMDD", "source": "그 날짜의 플랫폼", "price": "1000", "free": "무료|유료", "title": "", "isbn": "",
               "evidence": [{"url": "", "quote": ""}],
               "other_platforms": [{"platform": "", "date": "", "price": "", "quote": ""}]}],
 "price_per_episode": "", "price_reason": "",
 "rating": "", "adult": false, "rating_evidence": [{"url": "", "quote": ""}],
 "authors": [{"name": "", "role": "", "evidence": [{"url": "", "quote": ""}]}],
 "genre": "", "summary": "", "completed": true, "total_episodes": 0,
 "publisher_name": "", "publisher_place": "", "publisher_evidence": [{"url": "", "quote": ""}],
 "url_main": "", "url_work": "",
 "conflicts": [{"field": "", "publisher_says": "", "found": "", "chosen": "", "reason": ""}],
 "not_found": [{"what": "찾지 못한 값", "searched": ["어디를 어떻게 찾아봤는지"]}],
 "notes": "",
 "review": {"done": false, "findings": [], "resolved": []}
}
```
`count` 는 납본 건수(납본 단위의 수), `publisher_says` 는 출판사 엑셀에 적혀 있던 값 그대로(없으면 빈 문자열)다. 검사가 이 둘을 기준으로 삼는다.
`episodes` 의 `no` 는 납본 단위 번호다(1부터 count 까지).

## 4. 스스로 검사
결과 파일을 저장할 때마다 돌린다.

`{PY} -m kolis_tool check-research "jobs/<작업>/research.json"`

걸린 항목을 읽고 고친 뒤 다시 돌린다. 통과("통과")가 나올 때까지 반복한다. 값을 끝내 찾지 못했으면 `not_found` 에 어디를 찾아봤는지 적어야 통과한다. 검사를 통과시키려고 값을 지어내면 안 된다.

## 5. 검수받기
검사를 통과하면 `reviewer` 에이전트에게 맡긴다(Agent 도구). 넘길 말: 결과 파일 경로와 job.json 경로.
검수자의 지적을 하나씩 처리한다: 맞으면 고치고, 아니면 왜 아닌지 근거를 댄다. 처리 내용을 `review.findings` / `review.resolved` 에 적고 `review.done` 을 true 로 한다. 그다음 4번 검사를 다시 돌린다.

## 6. 배운 것 적기
이번에 새로 알게 된 요령을 `knowledge/platform-notes.md` 에 적는다. **파일 맨 위의 "적는 법"을 지킨다**: 주제별 단락(플랫폼·출판사·납품 자료·도구) 안에 적고, 작품 이름으로 단락을 만들지 않는다. 이미 적힌 내용과 같으면 새로 적지 말고 그 줄의 확인 횟수만 고친다. 적힌 내용이 틀렸으면 그 줄을 고친다.
적기 직전에 파일을 다시 읽는다(다른 작품을 맡은 에이전트가 그사이에 고쳤을 수 있다). 새로 알게 된 것이 없으면 아무것도 적지 않는다.

## 7. 끝
마지막 답: 결과 파일 경로, 최초 연재 플랫폼과 이유 한 줄, 엇갈림과 찾지 못한 값 목록.
